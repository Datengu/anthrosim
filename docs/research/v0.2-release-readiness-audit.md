# v0.2 release-readiness and pre-M9 audit

## Purpose

This audit asks two separate questions after completion of M8 and its post-milestone hardening:

1. Is the current M8 baseline mature enough to become the named `v0.2.0` software release?
2. After that release is frozen, is there any unresolved defect that should prevent AnthroSim from proceeding to M9 planning/design?

The audit is intentionally case-study-neutral. It assesses software, scientific-reproducibility and repository-governance readiness; it does not make an archaeological interpretation.

## Version decision

AnthroSim's release policy reserves `v0.2.0` for the audited and reverified M8 baseline. That is the appropriate next version.

`v0.1.0` closed the deterministic synthetic M1-M7 experiment-engine baseline. Since that closure, M8 added evidence-grounded normalized landscapes, explicit landscape-to-model transformations, spatial execution/observability, evidence identity and the first open-terrain null-model benchmark, followed by substantial provenance, persistence, validation, packaging and archive-integrity hardening.

This is a meaningful capability release rather than a compatible patch. It does not imply `1.0.0` or empirical validation of any historical population.

## Scientific re-verification

The strongest release-readiness check was direct comparison of a later full M8.6 rerun against the preserved reference.

The complete M8.6 benchmark was rerun successfully on PR #102 after the substantive post-M8 hardening through #94. The successful workflow artifact was inspected directly during this audit.

Result:

- all four predeclared arms retained the same classification state;
- all eight seeds per arm completed with the same authoritative terminal state digest;
- **32/32 terminal `stateDigest64` values matched the preserved M8.6 reference exactly**;
- the overall benchmark remained `fragile_spatial_structure`;
- primary metric classifications, paired signs and predeclared median effect summaries matched the preserved reference.

The aggregate's complete hash is expected to differ across source revisions because it contains provenance and experiment identities. Scientific comparison must therefore normalize expected source/release identity differences rather than compare the entire aggregate byte-for-byte.

This establishes that the post-M8 hardening did not silently change the preserved M8 scientific baseline.

## Positive findings

At the audit boundary:

- M8 is complete under the roadmap's stated acceptance boundary;
- the post-M8 #88-#95 integrity/hardening set has been implemented, with #88 reopened below for newly discovered governance drift;
- research archive SHA-256 integrity support is present;
- future event-storage scaling has a documented boundary without prematurely changing the simple small-run representation;
- no open implementation backlog existed before this release-readiness audit;
- no indexed `TODO`, `FIXME`, `HACK`, `unsafe`, `todo!`, `unimplemented!` or `panic!` shortcuts surfaced in the audit search;
- dependencies are locked and third-party CI actions are pinned;
- deterministic replay, checkpoint resume, source lineage, semantic bundle validation, cross-platform execution, landscape loading/preprocessing, spatial mechanisms, spatial observability, Explorer reconciliation, packing and source provenance have dedicated automated coverage;
- `MODEL_SEMANTICS_ID` remains `anthrosim-model-semantics-v1`; no release-only reason was found to change authoritative model semantics identity.

## Release blockers found

### #88 — branch-protection governance drift

The original #88 defect was corrected by adding the required scientific/integrity checks to `main`, but the live rule has drifted since then.

The audit found:

- required status checks are reported with enforcement level `non_admins`;
- the repository owner/account has admin permission, so normal administrator merges can bypass the required scientific gates;
- the post-#92 `New-directory resume Explorer compatibility` gate is not in the live required-check set;
- the CI topology document describes workflow responsibilities but not the exact branch-protection contract.

#88 is therefore reopened and is a `v0.2.0` release blocker. This is a governance defect, not evidence of a changed M8 simulation result.

### #106 — canonical M8.6 regression is not automatically enforced

The M8.6 workflow reruns and aggregates the predeclared benchmark but previously treated successful execution as sufficient. It did not compare the generated scientific baseline to the preserved reference.

A future authoritative change could therefore alter M8.6 state digests or paired-effect classifications while the workflow remained green.

Manual audit comparison established that no such drift exists today. #106 adds the missing automated provenance-normalized comparison and broadens trigger coverage so the release candidate and future authoritative core/CLI changes exercise it.

## Release task

#107 defines the `v0.2.0` release once #88 and #106 are resolved.

The release must:

- update package/Cargo/citation metadata consistently to `0.2.0`;
- describe v0.2 as the audited M8 evidence-grounded spatial experiment baseline;
- run the complete release verification set, including canonical M8.6 scientific regression;
- preserve the existing model-semantics identity unless an actual semantic incompatibility is discovered;
- document the current checkpoint compatibility rule: resume requires exact `modelVersion`, so a released v0.1.0 checkpoint is not resumable by a v0.2.0 executable under the present fail-closed policy;
- contain no M9 design or implementation.

## M9 readiness verdict

**Proceed to M9 planning/design only after `v0.2.0` is released and frozen.**

No M8 functionality gap was found that justifies inventing an M8.7/M8.8 feature phase. The remaining scientific limitations—synthetic demographic/resource/migration assumptions, lack of case-study calibration, uncertainty/observation modelling and question-specific archaeological validation—are explicit boundaries that later question-led work is expected to address. They are not evidence that M8 is incomplete.

The correct stopping boundary is therefore:

```text
M1-M7 / v0.1.0
    -> M8 implementation
    -> post-M8 integrity hardening
    -> v0.2 release-readiness audit
    -> resolve #88 and #106
    -> release/freeze v0.2.0 via #107
    -> STOP
    -> M9 planning/design begins only by a later explicit decision
```
