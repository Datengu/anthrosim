## Fresh adversary 2 — target-arrival reconsideration after same-day M4

Evidence PR: **#686**, evidence-only  
Evidence branch: `audit/v6-area-a-target-arrival-same-day-m4`  
Exact scientific evidence head: `bf94ed046df9d53889d1eacf43c57b52812bc1a7`  
Test: `crates/anthrosim-core/tests/audit_v6_area_a_target_arrival_same_day_m4.rs`  
Central CI run: `34301664858`  
`Quality and tests` job: `102309697902`

### Hypothesis

`TargetArrivalDay` reconsideration uses current persistent residence. If M4 changes residence on a fixed boundary and thereby makes the recomputed M9 departure equal to that same boundary day, the event-driven outer loop may re-enter M9 from `current_day` after M4 has already executed, creating a second logical pass through the day with reversed causal priority.

### Controlled construction

One declared household was configured so that:

- persistent residence initially equals Cell 1;
- Cell 1 movement cost is `65,000`, above the M9 traversal ceiling `10,000`, so the target-arrival journey is initially unreachable;
- the first M4 boundary is day **91**;
- M4 is deterministically forced to relocate Cell 1 → Cell 2 on day 91;
- Cell 2 → focal Cell 3 has accumulated travel cost `1,000`;
- travel capacity is `112` units/day, giving `ceil(1000 / 112) = 9` outbound days;
- target arrival is day **100**;
- therefore the post-M4 residence implies a newly recomputed M9 departure day of exactly **91**.

The final oracle inspected authoritative event sequence, not merely end state.

### Exact result

The harness reached the scientific assertion cleanly:

- `cargo fmt`: passed;
- Clippy: passed;
- all **284** pre-existing `anthrosim-core` unit tests passed immediately before the dedicated adversary;
- the dedicated adversary then failed.

Observed authoritative events:

```text
M4 HouseholdMigration       day 91, sequence 1
M9 TemporaryJourneyDeparted day 91, sequence 2
```

Failure text:

```text
same-day scheduler inversion: M4 migration sequence 1 ran before newly due M9 departure sequence 2 on day 91; declared fixed-day order requires M9 before M4
```

### Mechanism

At the fixed boundary, ordinary M9 processing happens before M4 as intended. M4 then changes persistent residence while simulation time remains on day 91. Before the next fixed boundary, `process_temporary_boundaries_before(...)` searches from the current simulation day. Target-arrival evaluation is recomputed from the changed residence. Because the new departure date equals day 91, M9 processes that departure after M4 has already completed.

This is not just log ordering: the M9 journey is created from the post-M4 residence and becomes authoritative state after the day’s declared M9 phase has already passed.

## Finding AV6-001 / #687

**Severity: P1 — material scientific conclusion risk.**

The supported M4×M9 system becomes scheduler-order dependent while the executable/documented model claims a fixed same-day causal order. This can alter target-arrival aggregation participation, visitor/transit person-days, duration-aware resource attribution, later crowding/resource pressure and downstream M4 feedback.

Historical overlap was searched before issue creation. The nearest prior issue is #197, repaired by PR #295. That earlier defect concerned an obsolete residence permanently preventing a later **future** valid departure. Its acceptance coverage includes initially unreachable/too-far → move → future valid departure and move-farther → missed-window cases. It does not cover the exact-boundary condition demonstrated here where the M4 residence change makes the newly required departure equal to the M4 day itself.

The distinct finding is preserved as:

- `AV6-001`;
- issue **#687**;
- P1;
- Area A primary;
- Areas E/F and D/N cross-cutting.
